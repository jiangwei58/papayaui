# 常见反模式与修正

## 内置样式反模式

1. 反模式：所有间距、排版都写内联样式。
   修正：优先改为 `m-*`、`p-*`、`text-*`、`flex` 工具类。
2. 反模式：使用不在约定范围的类值。
   修正：使用文档约定范围，并优先选可被 `2` 或 `5` 整除的值。
3. 反模式：工具类和冲突自定义样式混用在同一节点。
   修正：保持工具类语义稳定，冲突样式改为业务类并拆分节点。

## pa-container 反模式

1. 反模式：页面不使用 `pa-container`，固定头底全部手写定位。
   修正：页面根节点改为 `pa-container`，固定区放入 `header`/`bottom`。
2. 反模式：头部或底部高度变化后不刷新容器计算。
   修正：结构变化后调用 `containerRef.value?.updateHeight()`。
3. 反模式：把可滚动的大块内容塞进 `header`。
   修正：`header` 仅放轻量固定内容，大块内容放默认插槽。

## useList 反模式

1. 反模式：筛选变更后不重置，直接请求下一页。
   修正：固定流程 `reset -> getData`。
2. 反模式：在多个函数重复增加 `pageNumber`。
   修正：仅在触底回调递增一次。
3. 反模式：并发请求时旧响应覆盖新响应。
   修正：使用 `key` 方案保证最新请求优先。

## pa-form 反模式

1. 反模式：`prop` 与规则 key 不一致。
   修正：路径字符串保持一一对应。
2. 反模式：提交前不做前端校验。
   修正：提交动作必须由 `validate` 结果控制。
3. 反模式：动态列表项使用固定规则路径。
   修正：用 `list.${index}.field` 动态路径。
4. 反模式：条件校验写死为 `required`。
   修正：使用 `validator` 根据联动字段动态判断。

## request 反模式

1. 反模式：业务代码散落 `uni.request`，无统一拦截。
   修正：统一通过 `papayaui/request` 实例发请求。
2. 反模式：请求失败只打印日志，不中断业务流程。
   修正：响应拦截返回 `false` 并让调用方处理失败分支。

## theme 反模式

1. 反模式：为改颜色直接修改组件源码。
   修正：通过 `--pa-*` 变量定制主题。
2. 反模式：页面内硬编码大量颜色值。
   修正：优先复用全局主题变量，页面仅覆盖差异变量。

## 评审检查清单

- 页面布局是否以内置样式为主。
- 页面骨架是否由 `pa-container` 承担。
- 列表分页是否走标准 `useList` 流程。
- 表单字段路径与规则是否严格对齐。
